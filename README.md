# 🛡️ OpenWrt to Wazuh SIEM: Custom Detection Engineering Lab

A comprehensive Blue Team engineering lab demonstrating end-to-end log collection, pipeline validation, live attack simulation, and custom detection rule authoring using a production OpenWrt edge device and Wazuh SIEM.

---

## 📋 Executive Summary

* **Objective:** Implement a secure telemetry and monitoring pipeline from a live network router to a centralized SIEM, emulate single-source and distributed authentication attacks against live hardware, and engineer custom correlation rules to address specific detection gaps.
* **Core Competencies:** Syslog transport configuration, log parsing and decoding, rule engineering, attack emulation, and incident detection lifecycle management.
* **Framework:** [MITRE ATT&CK](https://attack.mitre.org/) (Tactics: Credential Access | Technique: [T1110 - Brute Force](https://attack.mitre.org/techniques/T1110/)).

---

## 🏗️ Architecture & Pipeline Flow

The telemetry and detection workflow follows a structured, multi-phase pipeline from the network edge to the SIEM dashboard:

### Pipeline Stage Details:

1. **Network Transport:** Raw authentication events generated by the `dropbear` SSH daemon on the OpenWrt router are forwarded via Syslog over UDP port 514 to the Wazuh Manager.
2. **Pre-decoding & Decoding (Phases 1 & 2):** The Wazuh engine parses the raw syslog strings to extract critical contextual fields, including the source IP (`srcip`) and target username (`dstuser`).
3. **Detection & Correlation (Phases 3 & 4):** Standard rules handle isolated authentication failures and single-source bursts, while custom rules (`botnet.xml`) bridge coverage gaps for multi-source or coordinated attack vectors.

## Phase 1: Telemetry Setup & Syslog Ingestion

1. **Configure Wazuh Server Ingestion:**
Update the Wazuh manager configuration file (`/var/ossec/etc/ossec.conf`) to accept incoming syslog traffic:
```xml
<remote>
  <connection>syslog</connection>
  <port>514</port>
  <protocol>udp</protocol>
  <allowed-ips>YOUR_ROUTER_IP_ADDRESS</allowed-ips> 
</remote>

```


Restart the manager service to apply changes:
```bash
sudo systemctl restart wazuh-manager

```


2. **Configure OpenWrt Remote Logging:**
Log into the OpenWrt Web Interface (LuCI) via your default gateway:
* Navigate to **System > System**.
* Select the **Logging** tab.
* Under **Log output** / **Remote logging**:
* **Log remote server:** Enter the IP address of the Wazuh Manager.
* **Remote port:** Set to `514`.
* **Remote protocol:** Select `UDP`.


* Click **Save & Apply**.


3. **Verify Log Transmission:**
Confirm receipt of raw telemetry packets on the Wazuh server interface:
```bash
sudo tcpdump -i any port 514 -v

```


Trigger an SSH connection attempt to the router from a separate terminal to validate packet flow:
```text
14:29:00.373095 enp0s3 In  IP (tos 0x0, ttl 64, id 26695, offset 0, flags [DF], proto UDP (17), length 114)
    _gateway.44278 > server1.syslog: SYSLOG, length: 86
        Facility authpriv (10), Severity info (6)
        Msg: Jul 20 14:29:00 OpenWrt dropbear[17955]: Child connection from <ATTACKER_IP>

```

## Phase 2: Pipeline Validation & Decoder Testing

1. Access the Wazuh Web Dashboard using your server IP address.
2. Isolate a clean log string from your `tcpdump` capture (starting at the timestamp, e.g., `Jul 20 14:29:00 OpenWrt dropbear...`).
3. Open the Wazuh navigation menu (top-left burger icon) and select **Ruleset Test** under **Server Management**.
4. Paste the log entry into the testing interface and run the evaluation. Confirm that the built-in `dropbear` decoders successfully parse the log across all operational stages.

## Phase 3: Attack Emulation & Baseline Analysis

To establish a baseline, simulate unauthorized authentication attempts against the live router environment using the automated script provided below.

### Attack Simulation Script (`bruteforceattack.py`) 
Provided in the repo

### Execution & Monitoring:

1. Install dependencies: `pip install paramiko`
2. Execute: `python3 bruteforceattack.py`
3. **Wazuh Monitoring:**
* Navigate to the **Wazuh Dashboard**.
* Open the **Discover** tab in the side navigation menu.
* Add custom columns/filters for `agent.id`, `rule.id`, `data.srcip`, and `rule.description` to review incoming telemetry.
* *Distributed Attack Note:* To emulate a botnet, execute the script simultaneously from multiple devices/IPs to see how the SIEM aggregates the events.

## Phase 4: Custom Detection Engineering (`botnet.xml`)

To address coverage gaps, deploy a custom rule definition to your Wazuh Manager rules directory:

```bash
sudo nano /var/ossec/etc/rules

```
add the botnet.xml file from the repo

### Finalization:

1. Restart the Wazuh Manager: `sudo systemctl restart wazuh-manager`
2. Re-run the simulation to verify the new rule fires in the **Discover** tab.
